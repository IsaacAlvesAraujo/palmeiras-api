1. Arquitetura

A aplicação usa Spring Boot para expor a API HTTP, Spring MVC para receber as requisições, Spring Data JPA para acessar o banco H2 e Jakarta Validation para validar os dados enviados.

CamadaResponsabilidade
ControllerRecebe HTTP, valida entrada e define respostas.
RepositoryConversa com o banco por meio do Spring Data JPA.
ModelRepresenta as entidades persistidas no banco.
OpenApiConfigDefine informações gerais da documentação.
Swagger UIPermite visualizar e executar os endpoints.

2. Paginação

Todos os endpoints de listagem usam Pageable. Isso significa que a API não precisa devolver todos os registros de uma vez.

Exemplo: GET /jogadores?page=0&size=5&sort=nome,asc
O índice começa em 0. Nesse exemplo, a API pede a primeira página, com no máximo 5 jogadores, ordenados pelo nome em ordem crescente.
ParâmetroFunçãoExemplo
pageNúmero da página, começando em 0.0
sizeQuantidade máxima de itens por página.5
sortCampo e direção da ordenação.nome,asc

A resposta Page também traz metadados como número da página, tamanho, quantidade total de elementos e quantidade total de páginas.

3. Recursos e endpoints

A API possui seis recursos. Cada um oferece CRUD completo e uma consulta personalizada paginada.

RecursoCRUDConsulta personalizada
JogadoresPOST/GET/PUT/DELETE /jogadoresGET /jogadores/buscar?nome=Raphael
EquipesPOST/GET/PUT/DELETE /equipesGET /equipes/buscar?nome=Palmeiras
EstádiosPOST/GET/PUT/DELETE /estadiosGET /estadios/buscar?nome=Allianz
ContratosPOST/GET/PUT/DELETE /contratosGET /contratos/buscar?duracaoMeses=24
SaláriosPOST/GET/PUT/DELETE /salariosGET /salarios/buscar?cargo=Analista
CampeonatosPOST/GET/PUT/DELETE /campeonatosGET /campeonatos/buscar?nome=Brasileiro

Em cada recurso, GET /recurso lista, GET /recurso/{id} busca, POST cria, PUT /{id} atualiza e DELETE /{id} remove.

4. Validação

Os modelos usam @NotBlank, @NotNull, @Size e @Positive. Quando um campo obrigatório não é enviado corretamente, a requisição é rejeitada com erro de validação.

POST /jogadores { "nome": "Nome do jogador", "posicao": "ATACANTE" }

6. Roteiro para testar a entrega

  1. Abra o projeto e execute a aplicação.
  2. Acesse /docs e depois clique em Abrir Swagger.
  3. Em Jogadores → POST, crie pelo menos 11 jogadores.
  4. Em Jogadores → GET, use page=0 e size=5.
  5. Teste page=1 e compare os registros retornados.
  6. Teste sort=nome,asc e depois sort=nome,desc.
  7. Busque um ID existente e depois um ID inexistente para conferir 200 e 404.
  8. Atualize um jogador com PUT e confirme com GET.
  9. Exclua um jogador e confirme que o GET daquele ID retorna 404.
Se o professor avaliar a paginação, o ponto principal está nos GETs de listagem: eles recebem Pageable e são representados por PagedModel, com metadados e links HATEOAS. O Swagger deve mostrar page, size e sort.
